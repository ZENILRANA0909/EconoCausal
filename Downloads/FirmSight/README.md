# FirmSight — IoT Firmware Emulation & Dynamic Analysis Sandbox

## Project Overview

FirmSight is a locally-run cybersecurity engineering platform for analyzing IoT
firmware binaries. It accepts uploaded firmware images, extracts their
filesystems, detects CPU architecture, performs static security analysis,
attempts QEMU-based emulation where the host supports it, simulates/observes
network activity, calculates an explainable threat score, and produces a
consolidated security report — all through a professional web dashboard.

This project was built as an Advanced Cybersecurity Engineering internship
project (Reverse Engineering / IoT Security track).

## Problem Statement

IoT devices frequently ship firmware with hardcoded credentials, unnecessary
network services (Telnet/FTP), embedded private keys, and other latent
security issues. Manually unpacking and reviewing firmware images is slow and
tool-fragmented. FirmSight consolidates the standard reverse-engineering
workflow (binwalk extraction → architecture detection → static analysis →
emulation → network observation → threat scoring → reporting) into a single
local application.

## Objectives

- Accept `.bin` / `.img` / `.fw` firmware uploads safely
- Extract firmware filesystems with Binwalk when available
- Detect firmware CPU architecture (ARM/MIPS/x86/PowerPC + endianness)
- Attempt QEMU emulation (full-system or user-mode) where supported
- Observe/simulate network activity generated by the firmware
- Run static security analysis for hardcoded secrets, risky services, and
  suspicious patterns
- Score and explain firmware risk (0–100, LOW/MEDIUM/HIGH/CRITICAL)
- Generate a downloadable security report
- Remain fully demonstrable even when Binwalk/QEMU/tcpdump are unavailable,
  via a clearly labeled DEMO / SIMULATED mode

## Architecture

```
Browser (React/TS dashboard)
        │  REST (JSON) over HTTP
        ▼
FastAPI backend (Python)
  ├── extraction/   binwalk wrapper + demo filesystem fallback
  ├── analyzers/    architecture detection + static rule engine
  ├── emulation/    QEMU process manager + demo boot simulator
  ├── networking/   tcpdump wrapper + pcap parser + demo network generator
  ├── detection/    explainable threat scoring engine
  ├── services/     orchestration layer (DB + analyzers + tools)
  └── storage/      SQLAlchemy models on SQLite
```

No Docker, no containers, no Kubernetes — everything runs as native OS
processes launched by the backend via `subprocess` with explicit argument
lists (never `shell=True`).

## Features

- Drag-and-drop firmware upload with SHA-256 calculation
- Binwalk-based filesystem extraction with automatic DEMO fallback
- Architecture detection via `file` / `readelf`
- Static analyzer for hardcoded IPs/URLs/credentials/private keys and risky
  binaries (telnet, ftp, wget, curl, netcat, busybox, reverse-shell patterns)
- Filesystem tree explorer highlighting security-relevant paths
  (`etc/passwd`, `etc/shadow`, `etc/init.d`, `www`, etc.)
- QEMU system/user-mode emulation manager with safe process lifecycle
  (start/stop/timeout/graceful termination) and automatic DEMO fallback
- tcpdump-based capture wrapper with a safe simulated network mode
- Explainable 0–100 threat scoring engine with human-readable reasons
- Consolidated JSON security report, downloadable from the dashboard
- Live system/tool status page (Python, Binwalk, QEMU, tcpdump, file,
  readelf)
- Structured application logging to `logs/firmsight.log`
- 57 backend pytest tests + frontend component tests

## Installation

### System Dependencies

FirmSight works without any of these installed (DEMO mode covers every
feature), but for real analysis install what you can:

**macOS:**
```
brew install binwalk qemu
# tcpdump, file, and readelf-equivalent tools are preinstalled or via binutils
brew install binutils
```

**Linux (Debian/Ubuntu):**
```
sudo apt update
sudo apt install -y binwalk qemu-system-arm qemu-system-mips qemu-user \
    qemu-system-x86 tcpdump file binutils
```

QEMU network capture (tcpdump) typically requires elevated privileges on
Linux. Either run the backend with `sudo`, or grant the capability:
```
sudo setcap cap_net_raw,cap_net_admin=eip $(which tcpdump)
```

### Python Setup

```
cd backend
python3 -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

### Frontend Setup

```
cd frontend
npm install
```

### Database Setup

No manual step required — SQLite is initialized automatically on backend
startup at `data/firmsight.db`.

### Environment Configuration

```
cp .env.example .env
```
Edit values if needed; the defaults work out of the box.

## Demo Mode

Because Binwalk, QEMU, and tcpdump may not be installed — or the uploaded
firmware may not correspond to a real, bootable image — FirmSight
automatically and transparently falls back to a synthetic **DEMO /
SIMULATED** mode at each stage:

- **Extraction:** if Binwalk is missing or extracts nothing, a synthetic
  firmware filesystem (`etc/passwd`, `etc/shadow`, `etc/init.d/S50telnet`,
  a fake reverse-shell script, etc.) is generated instead.
- **Emulation:** if no matching QEMU binary is installed, or the firmware
  isn't directly bootable/executable, a simulated boot log is returned.
- **Network:** simulated network events (DNS lookups, a Telnet connection,
  an FTP connection, a reverse-shell-style connection) are generated so the
  Network Monitor and Threat Detection pages remain demonstrable.

Every simulated result is labeled `is_demo: true` in the API and shown with
a **DEMO / SIMULATED** banner in the UI. FirmSight never presents simulated
results as real hardware analysis.

Generate a ready-to-upload synthetic sample firmware:
```
python3 scripts/generate_sample_firmware.py
```
This writes `samples/demo_router_firmware.bin`.

## Real Analysis Mode

With Binwalk, QEMU, and tcpdump installed, upload a real firmware image
(`.bin`/`.img`/`.fw`). FirmSight will:
1. Run real Binwalk extraction.
2. Detect real architecture via `file`/`readelf` on extracted executables.
3. Attempt real QEMU emulation matching the detected architecture (full
   system emulation for boards with a matching `qemu-system-*` binary, or
   user-mode emulation via `qemu-arm`/`qemu-mips` for standalone
   executables).
4. If the firmware cannot actually boot/execute (most firmware requires a
   full board/SoC definition QEMU doesn't ship generically), FirmSight
   reports this and falls back to DEMO mode rather than pretending it
   worked.

## QEMU Setup

FirmSight auto-detects these binaries via `PATH`:
`qemu-system-arm`, `qemu-system-aarch64`, `qemu-system-mips`,
`qemu-system-mipsel`, `qemu-system-x86_64`, `qemu-arm`, `qemu-mips`,
`qemu-mipsel`.

Install via `brew install qemu` (macOS) or the `qemu-system-*`/`qemu-user`
packages (Linux). Full-system emulation of arbitrary IoT firmware generally
requires a board-specific machine definition that stock QEMU does not
provide for most consumer routers/cameras — this is a known, documented
limitation of firmware emulation in general, not specific to FirmSight.

## Binwalk Setup

`brew install binwalk` (macOS) or `sudo apt install binwalk` (Linux).
FirmSight calls `binwalk --extract --directory <dir> <firmware>`.

## tcpdump Setup

Preinstalled on macOS; `sudo apt install tcpdump` on Linux. Capturing
traffic typically requires root privileges or the `cap_net_raw`/
`cap_net_admin` capabilities described above.

## Example Workflow

1. `make backend` (terminal 1)
2. `make frontend` (terminal 2)
3. Open `http://127.0.0.1:5173`
4. Go to **Firmware Upload**, upload `samples/demo_router_firmware.bin`
5. Click **Analyze** — this runs extraction and static analysis
6. Review **Filesystem Explorer** for the extracted tree
7. Review **Static Findings**, filter by severity
8. Go to **Emulation**, click **Start Emulation** (falls back to DEMO

9. Review **Network Monitor** for observed/simulated connections
10. Review **Threat Detection** for the explainable 0–100 score
11. Review **Security Report** and export as JSON

Total demonstration time: approximately 5–10 minutes.

## Limitations

- Full-system QEMU emulation of arbitrary consumer IoT firmware is not
  generally possible without board-specific machine definitions; FirmSight
  is transparent about this and falls back to DEMO mode rather than
  fabricating results.
- Network capture requires tcpdump and, on most systems, elevated
  privileges; without both, FirmSight uses simulated network events.
- Static analysis is pattern-based (regex/keyword matching against
  extracted file contents) — it flags indicators for human review and does
  not itself prove malicious intent.
- Designed for local, single-user academic demonstration; not hardened for
  multi-tenant or internet-facing deployment.

## Security Considerations

- Uploaded firmware is never executed directly on the host.
- All uploads are validated by extension and size before being written to
  disk with a sanitized filename.
- All subprocess calls use explicit argument lists (`shell=False`); no
  string-interpolated shell commands.
- Filesystem browsing resolves paths against the extraction root and
  rejects traversal outside it.
- Emulation processes are time-bounded and terminated gracefully
  (`SIGTERM` then `SIGKILL` on timeout).
- FirmSight never scans external networks or attacks real devices; all
  "network activity" is either passively observed from a local emulated
  process or clearly labeled as simulated.
